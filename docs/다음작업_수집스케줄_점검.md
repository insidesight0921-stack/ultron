# 다음 작업 — 일일 수집 스케줄 점검 (universe·ticker-map·factor 미갱신)

> 작성일: 2026-08-26 · 원인 확인, **코드 변경 불필요 / 내일 검증만 남음**
> 대상: launchd `com.hyunjun.ai-agent.market-data-collector`

## 1. 증상

`data/shareable/cache`의 갱신이 데이터셋별로 갈렸다.

| 데이터셋 | 최신 | 상태 |
|---|---|---|
| market_index (KOSPI) | 2026-08-26 매일 16:20 | ✅ 정상 |
| universe (KOSPI200) | 2026-08-24 | ❌ 이틀 정지 |
| ticker_map | 2026-08-23 | ❌ 정지 |
| factor_snapshot | 2026-08-21 | ❌ 정지 |

> 2026-08-26분 universe는 정기 수집이 아니라 `seed_watchlist_from_bots.py` 실행 중
> kium_bot이 pykrx로 직접 받아 저장한 것이다. 스케줄러 산출물이 아니다.

## 2. 원인 — KRX 응답 문제가 아니라 **설치된 plist의 인자**

`market_data_collector.py --dataset all`은 `collect_all_public()`을 타고
지수 → ticker-map → factor(KOSPI/KOSDAQ) → universe(3종)를 순서대로 수집한다.
실패는 데이터셋별로 격리돼 각각 `log.warning`을 남긴다.

그런데 실제 실행 로그는 이렇다.

```
out: [{"dataset": "market_index", "name": "KOSPI", ...}]      ← 배열 길이 1
err: VKOSPI 수집 건너뜀 (검증된 무인증 소스 없음)
```

`--dataset all`로 돌았다면 out에 ticker_map·factors·universe 항목이 함께 찍히거나,
실패했다면 err에 "ticker map 수집 건너뜀 / universe 수집 건너뜀" 경고가 남아야 한다.
**둘 다 없다** → 그 코드 경로가 아예 실행되지 않았다는 뜻이고,
설치돼 있던 plist가 지수만 받는 옛 인자였다고 보는 것이 맞다.

`agent_services.sh`의 현재 writer는 `--dataset all`을 넣는다. plist는 `install`
할 때만 다시 쓰이므로, 스크립트를 고친 뒤 재설치하지 않았다면 옛 인자가 계속 돈다.

## 3. 결과 — ✅ 해결됨 (2026-08-27 16:20 실행 확인)

재설치된 plist가 `--dataset all`로 실행돼 4개 데이터셋이 모두 갱신됐다.

```json
[{"dataset":"market_index","as_of":"20260827","rows":364},
 {"dataset":"ticker_map","as_of":"20260827","rows":2687},
 {"dataset":"factors","market":"KOSPI","as_of":"20260827","fundamental_rows":890,"market_cap_rows":917},
 {"dataset":"factors","market":"KOSDAQ","as_of":"20260827","fundamental_rows":1750,"market_cap_rows":1770},
 {"dataset":"universe", ...}]
```

- 캐시 생성 확인: `ticker_map_20260827.json`, `factors/factor_snapshot_{KOSPI,KOSDAQ}_20260827.json`,
  `universe_{KOSPI200,KOSDAQ150,KOSPI200+KOSDAQ150}_20260827.json`
- err 로그의 유일한 경고는 VKOSPI(무인증 소스 없음, 의도된 fail-closed). "수집 건너뜀" 다른 항목 없음.
- 원인 진단(설치된 plist의 옛 인자)이 맞았고, 2026-08-26 `agent_services.sh install`이 이를 교체했다.
- **남은 확인**: 다음 주 1회 더 관찰해 매일 갱신이 유지되는지 본다.

## 4. 조치 경위 — 이미 되었을 가능성이 높음(당시 판단)

2026-08-26 주간 리포트 잡을 추가하며 `agent_services.sh install`을 실행했다.
이때 collector plist도 현재 writer 기준으로 다시 쓰였을 것이므로,
**다음 16:20 실행부터 universe·ticker-map·factor가 함께 갱신되어야 한다.**

## 5. 검증 절차 (재발 시 사용)

```bash
# 1) out 로그에 데이터셋 4종이 찍히는지
grep -o '"dataset": "[a-z_]*"' data/private/logs/market_data_collector.out.log | sort | uniq -c

# 2) 캐시 파일이 당일 날짜로 생기는지
ls -t data/shareable/cache | grep -E "universe|ticker_map" | head
ls -t data/shareable/cache/factors | head
```

- 4종이 모두 찍히면 종료. 캐시 정지 문제 해결.
- 여전히 market_index만 찍히면 **설치된 plist를 직접 확인**한다.
  `plutil -p ~/Library/LaunchAgents/com.hyunjun.ai-agent.market-data-collector.plist`
  → `ProgramArguments`에 `--dataset all`이 있는지. 없으면 install이 덮어쓰지 못한 것이다.
- 인자는 맞는데 err에 "universe 수집 건너뜀"이 찍히면 그때는 진짜 KRX 응답 문제다.
  KRX_ID/KRX_PW 만료를 먼저 의심한다(2026-08 중순에 한 번 겪은 이력 있음).

## 6. 왜 방치하면 안 되나

지금은 universe 조회 실패 시 마지막 스냅샷으로 우회된다(`kium_bot.fetch_universe`,
`seed_watchlist_from_bots.py`). 며칠 차이는 KOSPI200 구성에 영향이 거의 없지만,
**분기 정기변경을 지나면 편입·제외된 종목을 계속 스캔하게 된다.**
편출 종목을 모멘텀 상위로 뽑는 일이 생기고, 그것을 알아채기 어렵다.

factor 스냅샷 정지는 더 직접적이다. 콴텍 추천이 8월 21일 fundamental로 계산된다.
